# KCP Rust SDK

Rust implementation of the [KCP — Knowledge Context Protocol](https://kcp-protocol.org)
SDK: an **embedded node** that signs, stores, searches and shares knowledge
artifacts produced by AI agents.

It is designed to be a drop-in peer of the reference Python SDK
(`sdk/python/kcp`) and of the Go SDK (`sdk/go`):

* **same canonical payload** — `json.dumps(to_dict(), sort_keys=True, separators=(",", ":"))`,
  including Python's `ensure_ascii=True` escaping,
* **same signatures** — Ed25519 over the canonical JSON, lowercase hex,
* **same content hashes** — SHA-256 of the *plaintext*, lowercase hex,
* **same private-content encryption** — HKDF-SHA256 key + AES-256-GCM with the
  `KCPENC1` wire magic,
* **same SQLite schema** — `kcp_artifacts`, `kcp_content`, `kcp_peers`,
  `kcp_sync_log`, `kcp_audit`, `kcp_config`, `kcp_sync_queue`,
  `kcp_replication` and the `kcp_fts` FTS5 index (`porter unicode61`).

Compatibility is enforced by cross-language test vectors generated by the
Python reference (see [Testing](#testing)), and by an end-to-end check where the
*Python* SDK reads and re-verifies a database written by the *Rust* SDK.

## Install

```toml
[dependencies]
kcp-sdk = { git = "https://github.com/kcp-protocol/kcp", branch = "main" }
```

`rusqlite` is built with the `bundled` feature, so SQLite (with FTS5) is
compiled from source — no system dependency, no C toolchain dance on Linux/macOS.

## Quick start

```rust
use kcp::{KCPNode, NodeConfig, PublishOptions};

let node = KCPNode::new(NodeConfig::new(
    "alice@acme.com",                    // user_id
    "acme-corp",                         // tenant_id
    "~/.kcp/kcp.db",                     // SQLite database
    "~/.kcp/keys",                       // Ed25519 keypair
))?;

// Publish a signed artifact.
let artifact = node.publish(
    "JWT Auth Guide",
    b"# JWT\n\nShort-lived tokens with rotating refresh keys.",
    PublishOptions::new()
        .format("markdown")
        .tags(vec!["auth".into(), "jwt".into()])
        .summary("How the auth service issues tokens"),
)?;

// Discover it.
let results = node.search("auth", 20)?;
assert_eq!(results.results[0].id, artifact.id);

// Verify it (tamper-evident).
assert!(node.verify(&artifact, None));

// Track provenance.
let derived = node.publish(
    "JWT Auth Guide (v2)",
    b"# JWT v2",
    PublishOptions::new().derived_from(&artifact.id),
)?;
assert_eq!(node.lineage(&derived.id)?.len(), 2);
# Ok::<(), kcp::KcpError>(())
```

## API

### `KCPNode`

| Method | Purpose |
|---|---|
| `KCPNode::new(NodeConfig)` | open the store, load/generate keys, persist identity (`node_id`, `user_id`, `tenant_id`, `public_key`) |
| `publish(title, content, PublishOptions)` | hash, sign, encrypt (if private) and store an artifact; returns `KnowledgeArtifact` |
| `publish_text(title, &str, opts)` | convenience wrapper for text content |
| `get(id)` / `get_content(id)` | metadata / content (`get_content` transparently decrypts own private artifacts) |
| `search(query, limit)` | FTS5 + BM25 full-text search |
| `list(limit, &tags)` | recent artifacts, optional tag filter |
| `verify(&artifact, pubkey?)` | verify the Ed25519 signature |
| `verify_signature(payload, hex_sig, pubkey?)` | verify a raw canonical payload |
| `lineage(id)` | full provenance chain, root → current |
| `derivatives(id)` | direct children of an artifact |
| `delete(id)` | soft-delete (audited) |
| `stats()` / `public_stats()` | full / sanitized statistics |
| `add_peer(url, name)` / `get_peers()` | peer registry |
| `export_artifact` / `export_to_file` / `import_from_dict` / `import_from_file` | offline sharing with signature verification |
| `can_decrypt(id)` | whether this node holds the artifact's content key |

### `LocalStore`

Direct SQLite access when you do not need the node identity: `publish`, `get`,
`get_content`, `search`, `list_artifacts`, `get_lineage`, `get_derivatives`,
`delete`, `import_artifact`, `get_artifact_with_content`, peers, config, audit,
sync queue (`enqueue_sync`, `dequeue_pending_sync`, `ack_sync`, `nack_sync`) and
replication (`record_replication`, `get_replication_status`).

### `crypto`

`generate_keypair`, `keypair_from_seed`, `derive_public_key`, `sign`, `verify`,
`hash_content`, `derive_content_key`, `encrypt_content`, `decrypt_content`,
`is_encrypted`, `save_keys`, `load_keys`, `load_or_generate_keys`.

## How signing works

```text
content            → SHA-256 (plaintext)               → content_hash
artifact.to_dict() → canonical JSON (no signature)     → payload
payload            → Ed25519(node private key)          → signature (hex)
```

`KnowledgeArtifact::canonical_json()` reproduces Python's
`json.dumps(..., sort_keys=True, separators=(",", ":"))` **byte for byte**,
including `ensure_ascii=True` escaping (`ção` → `\u00e7\u00e3o`, `🚀` →
`\ud83d\ude80`, tabs → `\t`). Required fields are always emitted, optional fields
only when set — the exact rules of the reference `to_dict()`.

## Testing

```bash
cargo test -j1
```

Test layout:

| Target | What it covers |
|---|---|
| `src/*` unit tests | canon encoder, crypto, models, store, node internals |
| `tests/vectors.rs` | cross-language vectors from the Python SDK (canonical payloads, signatures, hashes, HKDF keys, AES-GCM blobs, raw payload signing) |
| `tests/schema_compat.rs` | SQLite schema equality (tables, column order, indexes, FTS5 tokenizer, WAL) and reading Python-shaped rows |
| `tests/node_sdk.rs` | public API end-to-end (`publish`/`get`/`search`/`verify`/`lineage`/export/import/peers) |

Regenerate the Python vectors (one container at a time):

```bash
docker run --rm -v "$PWD:/w" -v /tmp/kcp-pylibs:/pylibs -e PYTHONPATH=/pylibs \
    python:3.12-slim python /w/sdk/rust/tests/fixtures/gen_vectors.py
```

Reverse-direction check — write with Rust, read + verify with Python:

```bash
cargo run --example roundtrip_write -- /tmp/kcp-db
docker run --rm -v "$PWD:/w" -v /tmp/kcp-pylibs:/pylibs -e PYTHONPATH=/pylibs \
    python:3.12-slim python /w/sdk/rust/tests/fixtures/verify_rust_db.py /tmp/kcp-db
```

## Known differences from the Python reference

These are deliberate, documented deviations — no silent incompatibilities:

1. **Content storage.** Rust stores content bytes in the `kcp_content` BLOB
   column (the schema's original semantics, same as the Go SDK). The Python
   SDK's Phase-3 filesystem shard store (`content/YYYY/MM/DD/<sha256>.bin`) is
   not re-implemented. Python still reads a Rust database correctly (it falls
   back to the BLOB and migrates it). A Python database whose content lives
   *only* in filesystem shards is not readable by Rust (`get_content` → `None`);
   metadata, signatures, lineage and search are unaffected.
2. **Empty search query** returns all non-deleted artifacts (the Go SDK's
   `LIKE` path behaviour). The Python FTS path would match nothing.
3. **FTS content indexing of encrypted blobs.** Rust never indexes ciphertext
   (it detects the `KCPENC1` magic). The Python reference checks for a stale
   `KCP1` prefix, so encrypted bytes can end up in its `content_text` column.
4. **Exotic float formatting.** Embedding floats are rendered with Python
   `repr()` conventions (`1.0`, `0.5`, `1e+20`, `1e-07`). Only values outside the
   ranges Python uses for its shortest-repr/exponent switch could differ.
5. **Transport is out of scope.** There is no HTTP server, no peer sync worker
   (`KCP_PEERS` is read and the sync queue is populated, delivery is up to the
   caller) and no `hub`/`client`/`identity` modules — this SDK covers the
   embedded node, storage and crypto surface of issue #3.
